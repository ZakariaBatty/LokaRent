## 1. Global Database Rules

### 1.1 — UUID Strategy

**Rule:** Every table has `id uuid PRIMARY KEY` as the unique identifier.

**Why:** UUIDs are globally unique, don't leak sequence information, and can be generated on the client. Human-readable IDs (invoice numbers, reservation codes) are stored separately in dedicated columns with gapless numbering.

**Standard:** UUID v7 (time-sortable, index-friendly, lexicographically orderable).

**Implementation:**
- Generated by database: `DEFAULT gen_random_uuid()` in Drizzle
- Generated by application: Pass UUID on insert if needed for transaction atomicity
- Foreign keys: Always UUID, never null unless explicitly documented

**Exception:** Synthetic compound keys use `(company_id, agency_id, entity_id)` for multi-tenant queries where UUID isn't sufficient.

---

### 1.2 — Tenant Scoping

**Rule:** Every business table carries `company_id uuid NOT NULL` and (optionally) `agency_id uuid`.

**Why:** Tenant isolation is a database-layer guarantee, not a code layer hope.

**Standard:**
- `company_id` is never null. It is the tenant root.
- `agency_id` is null for company-level records (subscriptions, company members, roles).
- `agency_id` is required for operational data (vehicles, reservations, customers, contracts).

**Example hierarchy:**
```
companies (1 row)
  ├── agencies (multiple rows, each with company_id)
  │     ├── vehicles (multiple rows, each with company_id + agency_id)
  │     ├── reservations (multiple rows, each with company_id + agency_id)
  │     └── members (company_id + agency_id, linking to company_memberships)
  └── company_memberships (company_id only, scoped to all agencies)
```

**Query pattern:** All queries start with `WHERE company_id = :company_id` (and `agency_id = :agency_id` for agency-scoped data).

---

### 1.3 — Timestamps

**Rule:** Every table has `created_at` and `updated_at` as `timestamptz`.

**Why:** Audit trail. Timezone-aware. Comparable.

**Standard:**
- `created_at`: Set once on insert. Never updated. Immutable.
- `updated_at`: Auto-set on insert. Updated on every mutation. Reflects the latest write time.
- Both are in UTC. Application layer converts to user timezone.

**Implementation:**
- `created_at DEFAULT now()` (immutable after insert)
- `updated_at DEFAULT now()` with trigger to update on every row change

**Exception:** Append-only tables (`audit_logs`, `activity_logs`, `vehicle_mileage_logs`) have `created_at` only.

---

### 1.4 — Soft Delete Strategy

**Rule:** Business data is never hard-deleted. Only soft-deleted via `deleted_at` and `deleted_by`.

**Why:** Legal hold. Audit trail. Reversal capability. Referential integrity.

**Standard:**
- Add `deleted_at timestamptz` (null = active, set = soft-deleted)
- Add `deleted_by uuid FK → users` (records who performed the delete)
- All queries filter `WHERE deleted_at IS NULL` by default
- Hard deletes are forbidden on business tables (companies, agencies, users, vehicles, customers, reservations, contracts, invoices, payments)

**Exception:** System reference tables (`permissions`, `roles`, `vehicle_categories`) and truly temporary data (`invitations`, `sessions`) can be hard-deleted after expiry.

**Reversal:** Set `deleted_at = NULL` and `deleted_by = NULL` to un-delete. No new table needed.

---

### 1.5 — Audit Requirements

**Rule:** Every insert, update, delete on business tables writes to `audit_logs`.

**Why:** Compliance. Forensics. Debugging.

**Standard:**
- `audit_logs` records `(table_name, row_id, operation, old_values, new_values, user_id, timestamp)`
- Append-only. Never updated or deleted.
- Partition by month after 6 months of hot storage.

**Operation values:** `'INSERT'`, `'UPDATE'`, `'DELETE'`, `'SOFT_DELETE'`.

**What NOT to audit:** `activity_logs`, `documents` file metadata (too noisy), session tables (too ephemeral).

---

### 1.6 — Naming Conventions

**Rule:** Consistent, predictable names.

**Tables:**
- Lowercase, snake_case, plural nouns: `vehicles`, `reservations`, `invoice_line_items`
- Parent-child: `contracts` + `contract_signatures` (not `signatures` alone)
- Lookup tables: `vehicle_categories`, `expense_categories`, `reservation_sources`

**Columns:**
- Lowercase, snake_case: `full_name`, `phone_number`, `created_at`
- Foreign keys: `{parent_table_singular}_id`: `user_id`, `agency_id`, `invoice_id`
- Booleans: `is_*`: `is_primary`, `is_system`, `is_active`
- Enums: `status`, `type`, `state` (never `state_type`)
- Timestamps: `created_at`, `updated_at`, `deleted_at`, `expires_at`, `verified_at`

**Enums:**
- Lowercase, snake_case values: `'active'`, `'pending'`, `'cancelled'`
- Scoped to entity: `reservation_status` not `status` (enum type name in Drizzle)
- Catalog: Every enum has a documented list of valid values in this spec

---

### 1.7 — Enum vs Lookup Table Strategy

**Rule:** Use lookup tables for user-editable values. Use enums for system values.

**Why:** Lookup tables allow runtime queries (SELECT * FROM vehicle_categories). Enums are immutable code. Mixing causes the enum to be the source of truth, forcing code deploys for data changes.

**Standard:**
- **Enums:** `reservation.status` (active, pending, completed, cancelled — never added by users)
- **Lookup tables:** `vehicle_categories` (SUV, sedan, truck — updated when agency needs new type)

**When to add a lookup table:** If users can create, edit, or name the value, use a lookup table.

**Phase 1 lookup tables:** `vehicle_categories`, `expense_categories`, `reservation_sources`, `roles` (custom)

---

### 1.8 — JSON Usage Policy

**Rule:** JSON is allowed only for semi-structured, rarely-queried data.

**Why:** Preventing a creep toward document databases.

**Allowed:** 
- `agencies.address` (JSONB `{ street, city, postal_code, country }`) — queried rarely, structure evolves slowly
- `settings.value` (text, but stores JSON strings) — configuration is untyped
- `contracts.template_snapshot` (JSONB) — frozen contract HTML + structured data
- `reservation_pricing_snapshots.snapshot_data` (JSONB) — immutable pricing record
- `documents.metadata` (JSONB) — file-specific attributes

**Forbidden:**
- No `json_column` for mutable data that needs filtering (e.g., "find all reservations with GPS selected"). Use normalized tables instead.
- No nested objects more than 3 levels deep (makes migrations hard).

**Query limitation:** Postgres can query JSON, but it's slow on large datasets. JSON is for write-once or read-full-record use cases, not for `WHERE json_column->>'field' = value`.

---

### 1.9 — Money Storage

**Rule:** Store money as `NUMERIC(14, 4)` (not float). Store the currency on financial rows where the certified Prisma schema includes it.

**Why:** Floating-point precision. Accounting requires exact representation. The certified Prisma schema uses four-decimal precision for rental, tax, and finance calculations.

**Standard:**
- Column name: `amount`, `total`, `price`, `tax` (never `price_usd` or currency-suffixed)
- Type: `NUMERIC(14, 4)` — matches the certified Prisma `Decimal(14,4)` convention
- Default currency: Inherited from `company.currency` or `agency.currency` when creating scoped rows
- Example: `invoices.total NUMERIC(14, 4)` with `invoices.currency`

**Currency aggregation:** Until an FX/conversion model exists, finance reports must group or filter by currency and must not aggregate different currencies into one total.

---

### 1.10 — Timezone Policy

**Rule:** Store all times in UTC. Convert to user timezone on read.

**Why:** Unambiguous, comparable across regions, avoids DST bugs.

**Standard:**
- Column type: `timestamptz` (PostgreSQL stores as UTC, displays in user's set timezone)
- All inserts: `now()` at database time (UTC)
- All queries: No timezone conversion at DB layer; application handles display
- User-specific: `users.timezone` is their preferred IANA zone for display only

**Deadline handling:** Dates are stored as `date` type (no time component). For "by end of day in the user's timezone," store the UTC datetime of midnight-next-day in the user's zone.

---

### 1.11 — Optimistic Locking Policy

**Rule:** Use `updated_at` for optimistic concurrency control. No pessimistic locking.

**Why:** Prevents thundering herd under contention. Allows long-running transactions to fail cleanly.

**Pattern:**
```
UPDATE reservations 
SET status = 'confirmed', updated_at = now()
WHERE id = :id AND updated_at = :client_updated_at
```
Result: 0 rows updated = conflict. Application retries with fresh data.

**Where NOT to use:** Critical operations (invoice generation, payment processing). Those use row locks in transactions (see Concurrency Rules).

---

### 1.12 — Versioning Strategy

**Rule:** Immutable snapshots for data that drives downstream decisions. New rows for corrections.

**Why:** Audit trail. Reversal capability. Legal defensibility.

**Examples:**
- `reservation_pricing_snapshots`: Write once, never update. A price change creates a new snapshot with `supersedes_id` reference.
- `contracts`: Each generated contract references the exact `contract_template_version` used. Template changes don't retroactively affect old contracts.
- `invoices`: Never updated. A correction issues a `credit_note`.

**Pattern:** Never mutate after "lock point." Create new versioned row instead.

## 2. Table Specifications

### Universal Column Contract

Every business table carries these columns — no exceptions:

| Column | Type | Constraint | Notes |
|--------|------|-----------|-------|
| `id` | `uuid` | PRIMARY KEY | UUID v7, auto-generated |
| `company_id` | `uuid` | NOT NULL FK | Tenant root. Never null. |
| `agency_id` | `uuid` | FK | Null for company-level. Required for operational data. |
| `created_at` | `timestamptz` | NOT NULL | Auto-set, immutable |
| `updated_at` | `timestamptz` | NOT NULL | Auto-updated on every change |
| `deleted_at` | `timestamptz` | | Soft delete. Null = active. |
| `deleted_by` | `uuid` | FK → users | Who soft-deleted this row. |

---

### Domain 1 — Multi-Tenant

#### `companies`

**Purpose:** The tenant root. One record per customer organization.

**Business Rules:**
- Immutable after creation: `slug`, `country_code`, `timezone`, `currency`, `language`
- `plan_id` is set at creation and can be changed via subscription upgrade
- `status` transitions: `'trial'` → `'active'` (after payment) or `'cancelled'` (if not renewed)

**Created By:** Registration flow. System account.

**Updated By:** Account owner (name, branding) or billing system (plan, status).

**Can Be Deleted?** No. Historical record. Soft-delete only.

**Soft Delete?** Yes. Prevents account resurrection bugs and keeps audit trail.

**Audit Required?** Yes. Every mutation.

**Events Produced:** `CompanyCreated`, `CompanyUpgraded`, `CompanyCancelled`, `CompanySuspended`

**Files Attached?** Yes: company logo (via `documents` polymorphic table).

**Indexes Needed:**
- `UNIQUE(slug)` — quick company lookup by slug for routing
- `UNIQUE(id, company_id)` — standard compound index

**Dependencies:**
- Referenced by `agencies`, `users`, `plans` (via `plan_id`), `settings`
- No dependencies on other tables

**Future Extensions:**
- `billing_accounts` (Phase 2): Add `billing_account_id` FK when Stripe integration lands
- `white_label_config` (Phase 3): Add `white_label_id` FK

---

#### `agencies`

**Purpose:** An operational branch within a company.

**Business Rules:**
- `code` is human-readable, unique per company (e.g., "CAS", "MAR")
- Cannot be created if company subscription limit `max_agencies` is reached
- Inherits defaults from company but can override `country_code`, `timezone`, `currency`
- `status` tracks operational state; agents see only `'active'` agencies

**Created By:** Company owner or account admin via Workspace UI.

**Updated By:** Company owner or admin (name, code, contact info, address).

**Can Be Deleted?** Logically, no. Soft-delete only. Has associated data.

**Soft Delete?** Yes.

**Audit Required?** Yes. Every mutation.

**Events Produced:** `AgencyCreated`, `AgencyUpdated`, `AgencyDeactivated`

**Files Attached?** No.

**Indexes Needed:**
- `UNIQUE(company_id, code)` — quick lookup within company
- `INDEX(company_id, deleted_at IS NULL)` — list active agencies

**Dependencies:**
- Parent: `companies`
- Referenced by: `vehicles`, `reservations`, `customers`, `users` (agency_memberships), `contracts`, `invoices`, `settings`, `audit_logs`

**Future Extensions:**
- Multi-location features (Phase 3): Add `parent_agency_id` for branch hierarchies

---

### Domain 2 — Identity

#### `users`

**Purpose:** Platform-level identity. A person who logs in.

**Business Rules:**
- Email is unique per company (`UNIQUE(company_id, email)`)
- User cannot be created if company subscription limit `max_users` is reached
- User can be a member of multiple agencies within the same company
- `last_login_at` is updated on every successful login (not audited to avoid noise)

**Created By:** Registration flow (self-signup) or admin invitation.

**Updated By:** User themselves (profile) or admin (deactivation).

**Can Be Deleted?** No. Historical record. Soft-delete only.

**Soft Delete?** Yes. Preserves audit trail.

**Audit Required?** Yes, except for `last_login_at` (too frequent).

**Events Produced:** `UserCreated`, `UserDeactivated`, `UserReactivated`

**Files Attached?** Yes: avatar (via `documents` polymorphic table).

**Indexes Needed:**
- `UNIQUE(company_id, email)` — quick login lookup
- `INDEX(company_id, deleted_at IS NULL)` — list active users

**Dependencies:**
- Parent: `companies`
- Referenced by: `company_memberships`, `agency_memberships`, `invitations`, `audit_logs`, `activity_logs` (via `user_id` and `actor_id`)

---

#### `roles`

**Purpose:** Named permission presets. Scoped per company.

**Business Rules:**
- System roles (`'owner'`, `'admin'`, `'agent'`) are seeded at company creation with `is_system = true`
- System roles cannot be deleted, renamed, or have permissions changed
- Custom roles can be created if company plan includes `'custom_roles'` feature
- Scope is either `'company'` (for company_memberships) or `'agency'` (for agency_memberships)

**Created By:** Admin or owner (custom roles only). System roles pre-seeded.

**Updated By:** Admin (name, description, permissions).

**Can Be Deleted?** System roles: no. Custom roles: only if no members have it.

**Soft Delete?** No (reference table).

**Audit Required?** Yes. Permissions changes are sensitive.

**Events Produced:** `RoleCreated`, `RolePermissionsChanged`, `RoleDeleted` (custom only)

**Files Attached?** No.

**Indexes Needed:**
- `UNIQUE(company_id, name, scope)` — quick lookup, scoped to scope
- `INDEX(company_id, is_system)` — list custom vs system roles

**Dependencies:**
- Parent: `companies`
- Referenced by: `company_memberships`, `agency_memberships`, `invitations`, `role_permissions`

---

#### `permissions`

**Purpose:** Flat registry of all grantable actions.

**Business Rules:**
- Seeded at deploy time. Never created by users. Platform read-only.
- Format: `{domain}.{action}` (e.g., `'reservations.create'`, `'fleet.delete'`)
- New permissions added via code deployment, not user UI
- Expense mutations use explicit finance keys: `finance.expenses.edit` and `finance.expenses.delete`.

**Created By:** System (seed script at deploy).

**Updated By:** Never (immutable reference data).

**Can Be Deleted?** No.

**Soft Delete?** N/A

**Audit Required?** No (immutable).

**Events Produced:** None (system table).

**Files Attached?** No.

**Indexes Needed:**
- `UNIQUE(key)` — quick lookup by permission

**Dependencies:**
- Referenced by: `role_permissions`, permission resolution at runtime

#### `role_permissions`

**Purpose:** Many-to-many join between roles and permissions.

**Business Rules:**
- A role has one or more permissions
- Adding/removing a permission from a role affects all members of that role immediately
- Cannot add permission to system role (immutable)

**Indexes Needed:**
- `UNIQUE(role_id, permission_key)` — prevent duplicates
- `INDEX(permission_key)` — find all roles with permission X

---

#### `company_memberships`

**Purpose:** Links a user to their company-level role.

**Business Rules:**
- One row per user (one company per user in Phase 1)
- `role_id` must have `scope = 'company'`
- Changing role affects all agency memberships below (cascading permission check)

**Indexes Needed:**
- `UNIQUE(company_id, user_id)` — one membership per user per company
- `INDEX(company_id, role_id)` — find all users with role X

---

#### `agency_memberships`

**Purpose:** Links a user to a specific agency with an agency-level role.

**Business Rules:**
- A user can have multiple rows (one per agency they can access)
- `role_id` must have `scope = 'agency'`
- Cannot create if company subscription limit `max_users` exceeded
- `is_primary` indicates the default agency on login; only one `true` per user

**Indexes Needed:**
- `UNIQUE(agency_id, user_id)` — one membership per user per agency
- `INDEX(user_id, is_primary)` — quick lookup of primary agency on login
- Partial unique on `(user_id, deleted_at IS NULL) WHERE is_primary = true` — enforce single primary

---

#### `invitations`

**Purpose:** Pending invitations before acceptance and membership creation.

**Business Rules:**
- One pending invitation per email per company (`UNIQUE(company_id, email)`)
- Token is hashed before storage (never stored plaintext)
- Expires after 7 days (checked at acceptance)
- On accept: Create user (if new) → create company_membership → create agency_membership (if `agency_id` set) → mark accepted

**Indexes Needed:**
- `UNIQUE(company_id, email)` — one pending invite per email
- `INDEX(token_hash)` — lookup by token (hashed)

## 3. Transactions

Every database transaction below must be atomic or explicitly fail with rollback rules documented.

### Transaction 1 — Register Company

**Tables touched:** `companies`, `agencies`, `users`, `company_memberships`, `agency_memberships`, `roles`, `role_permissions`, `plan_limits` (read-only)

**Atomic?** Yes. All-or-nothing.

**Sequence:**
1. Check company limit: Can we create one more company on the plan? (Not applicable for new signups, but validated)
2. Insert `companies` row with `plan_id = 'starter'`, `status = 'trial'`
3. Insert default `agencies` row with company_id
4. Insert `users` row for account owner
5. Seed system `roles` (`owner`, `admin`, `agent`) for this company
6. Seed `role_permissions` for each role (read from platform seed data)
7. Create `company_memberships` linking user to owner role
8. Create `agency_memberships` linking user to owner role for the default agency with `is_primary = true`

**Rollback rules:** If any step fails, rollback all. User sees: "Registration failed. Try again or contact support."

**Failure cases:**
- Email conflict: Reject with "Email already exists"
- Plan limit (theoretically, shouldn't apply on signup): Reject with "Cannot process — contact support"
- Database error: Rollback, user retries

---

### Transaction 2 — Create Reservation

**Tables touched:** `reservations`, `reservation_pricing_snapshots`, `reservation_extras`, `vehicles` (read for availability), `customers` (read), `plan_limits` (read)

**Atomic?** Yes.

**Sequence:**
1. Validate customer exists and not blacklisted
2. Lock `vehicles` row with `FOR UPDATE` to check availability (no existing reservation overlaps)
3. Check subscription limit: `max_reservations_per_month` for this month
4. Calculate pricing snapshot (base rate × days + extras)
5. Insert `reservations` row with `status = 'pending'`
6. Insert `reservation_pricing_snapshots` row (immutable)
7. Insert `reservation_extras` rows (GPS, baby seat, etc.)
8. Insert `reservation_timeline_events` row: `{'type': 'created', 'actor': user}`
9. Write `activity_log`: "Ahmed created reservation RES-2024-1234"
10. Write `audit_logs`: Full before/after

**Rollback rules:** If vehicle unavailable, reject immediately. If pricing calc fails, rollback all.

**Failure cases:**
- Vehicle not available: "Vehicle is booked for those dates"
- Customer blacklisted: "Customer cannot be rented to"
- Limit exceeded: "Monthly reservation limit reached"

---

### Transaction 3 — Pickup Vehicle

**Tables touched:** `reservations`, `contracts`, `vehicle_mileage_logs`, `reservation_timeline_events`

**Atomic?** Yes.

**Sequence:**
1. Load reservation (must be `status = 'confirmed'`)
2. Load contract (must be `status = 'signed'`)
3. Load vehicle and current mileage
4. Record mileage: Insert `vehicle_mileage_logs` row with `event = 'pickup'` and meter reading
5. Record contract pickup: Insert `contract_inspection_items` "pickup inspection" (state, fuel, damage)
6. Update `reservations.status = 'active'`, `updated_at = now()`
7. Insert `reservation_timeline_events` row: `{'type': 'picked_up'}`

**Rollback rules:** If mileage reading fails (invalid), reject and don't update reservation status.

---

### Transaction 4 — Return Vehicle

**Tables touched:** `reservations`, `contracts`, `vehicle_mileage_logs`, `invoices`, `invoice_line_items`, `deposits`, `reservation_timeline_events`

**Atomic?** Yes, but complex.

**Sequence:**
1. Load reservation (must be `status = 'active'`)
2. Load contract
3. Record return mileage: Insert `vehicle_mileage_logs` row with `event = 'return'`
4. Calculate rental days: `return_date - pickup_date`
5. Load pricing snapshot and calculate final invoice:
   - Base: `daily_rate × days`
   - Late return fee: if `return_date > due_date`, add `(late_days × late_fee_rate)`
   - Damage: if damages recorded, add to invoice
   - Deposit: Apply deposit release (if held) or charge (if damage exceeds deposit)
6. Generate invoice: Insert `invoices` row
7. Insert `invoice_line_items` (rental, late fee, damage, etc.)
8. If deposit held: Insert `deposits` row with `status = 'released'` and `released_at = now()`
9. Update `reservations.status = 'completed'`
10. Insert `reservation_timeline_events` row: `{'type': 'returned'}`

**Rollback rules:** If invoice generation fails, rollback all. Reservation stays `'active'`.

## 4. Concurrency Rules

### Race Condition 1 — Two Agents Booking Same Vehicle

**Scenario:** Agent A and Agent B simultaneously try to book vehicle X for the same dates.

**Prevention:**
```sql
BEGIN;
SELECT id FROM vehicles WHERE id = :vehicle_id FOR UPDATE;  -- Row-level lock
SELECT * FROM reservations 
  WHERE vehicle_id = :vehicle_id 
  AND deleted_at IS NULL
  AND NOT (end_date <= :requested_start_date OR start_date >= :requested_end_date);
-- If any rows found, commit and reject request
-- If no rows found, insert new reservation
COMMIT;
```

**Result:** One succeeds, one gets "Vehicle is booked for those dates."

---

### Race Condition 2 — Two Payments Simultaneously

**Scenario:** Payment system processes payment + user manually pays invoic.

**Prevention:**
```sql
UPDATE invoices 
SET status = 'paid', paid_at = now()
WHERE id = :invoice_id AND status = 'unpaid'
```
Result: Only one UPDATE succeeds (1 row updated). Second gets 0 rows and must refresh invoice state.

---

### Race Condition 3 — Invoice Numbering (Gapless)

**Scenario:** Two invoices generated simultaneously. Both need unique sequential `invoice_number`.

**Prevention:** Use `number_sequences` table with row locking:
```sql
BEGIN;
SELECT next_value FROM number_sequences 
  WHERE company_id = :company_id AND sequence_key = 'invoice_number'
  FOR UPDATE;
UPDATE number_sequences 
  SET next_value = next_value + 1
  WHERE company_id = :company_id AND sequence_key = 'invoice_number'
  RETURNING next_value;
INSERT INTO invoices (invoice_number, ...) VALUES (:next_value, ...);
COMMIT;
```

Result: Gapless numbering guaranteed. Both transactions serialize; one waits for the other.

---

### Race Condition 4 — Vehicle Availability Block Conflict

**Scenario:** Maintenance scheduled for same dates as reservation.

**Prevention:**
```sql
SELECT * FROM vehicle_availability_blocks 
  WHERE vehicle_id = :vehicle_id 
  AND deleted_at IS NULL
  AND NOT (end_date <= :requested_start_date OR start_date >= :requested_end_date);
-- If found, reject reservation
```

---

### Race Condition 5 — Primary Agency Switching

**Scenario:** User has two agencies; both marked `is_primary = true`.

**Prevention:** Partial unique index:
```
UNIQUE(user_id, deleted_at IS NULL) WHERE is_primary = true
```

Database enforces one primary per active user. Update attempts to set a second primary fail.

---

### Race Condition 6 — Company Suspension

**Scenario:** User tries to create reservation while company status changes to `'suspended'`.

**Prevention:** All create operations check company.status first:
```sql
SELECT status FROM companies WHERE id = :company_id;
-- If not 'active' or 'trial', reject operation
```

## 5. Validation Rules

### Category 1 — Unique Validations

| Entity | Fields | Scope | Rule |
|--------|--------|-------|------|
| companies | slug | global | slug is unique across all companies |
| users | email | per company | email is unique per company |
| agencies | code | per company | code (e.g., "CAS") is unique per company |
| vehicles | plate | per company | plate is unique per company |
| customers | tax_id | per company | tax_id (if provided) is unique per company |
| invitations | email | per company | only one pending invite per email per company |
| roles | (name, scope) | per company | role name is unique per company + scope |
| agency_memberships | (user_id, agency_id) | enforced | one membership per user per agency |
| company_memberships | (user_id, company_id) | enforced | one membership per user per company |
| contract_templates | (name, is_active) | per company | only one active template at a time (optional rule) |

---

### Category 2 — Foreign Key Validations

Every FK is enforced at the database level. Violation = insert/update rejected.

| FK Column | References | Delete Rule | Notes |
|-----------|------------|------------|-------|
| companies.plan_id | plans.id | RESTRICT | Cannot change plan if actively using limits |
| agencies.company_id | companies.id | RESTRICT | Cannot delete company while agencies exist |
| users.company_id | companies.id | RESTRICT | Cannot delete company while users exist |
| reservations.customer_id | customers.id | RESTRICT | Cannot delete customer with pending/active reservations |
| reservations.vehicle_id | vehicles.id | RESTRICT | Cannot delete vehicle with pending/active reservations |
| invoices.reservation_id | reservations.id | RESTRICT | Cannot delete reservation with invoices |
| contracts.reservation_id | reservations.id | RESTRICT | Cannot delete reservation with contracts |

---

### Category 3 — Business Validations

**Reservation validation:**
- `start_date < end_date` (enforced via CHECK constraint)
- Reservation duration >= 1 day
- `start_date >= today` (must book future)
- Customer exists and not blacklisted
- Vehicle status = `'active'`
- No overlapping reservations for same vehicle

**Customer validation:**
- Customer type must be `'individual'` or `'company'`
- If `'individual'`: `customer_individuals` row must exist
- If `'company'`: `customer_businesses` row must exist
- Required fields populated based on type

**Invoice validation:**
- `status` transitions: `'draft'` → `'issued'` → `'paid'` or `'overdue'` → `'cancelled'`
- Cannot issue if customer blacklisted
- Total must equal sum of line items
- `type = rental` requires `reservation_id`; `type = manual` requires `reservation_id IS NULL`
- Manual invoices require an existing scoped customer and at least one manual line item
- Issued invoices must use `invoice_line_items.tax_rate` and `invoice_line_items.tax_amount` as the historical tax snapshot. Never recalculate issued invoice tax from current settings.

**Payment validation:**
- `amount_paid > 0`
- Cannot overpay (amount paid ≤ invoice total) — can be relaxed for credit scenarios
- Payment date cannot be in the future

---

### Category 4 — Date Validations

**Global rule:** All dates are `date` type (no time). Datetimes are `timestamptz`.

**Reservation dates:**
- `start_date` and `end_date` are dates (noon UTC)
- At least 1 day apart
- Cannot be in the past

**Document expiry:**
- `vehicle_registrations.expires_at`, `vehicle_insurances.expires_at` trigger alerts 30 days before
- Alert query: `WHERE expires_at BETWEEN today() AND today() + interval '30 days'`

**Invitation expiry:**
- `invitations.expires_at` is set to `now() + interval '7 days'`
- On accept, check: `IF now() > expires_at, reject with 'Invitation expired'`

---

### Category 5 — Money Validations

**All money columns (certified Prisma schema: NUMERIC(14,4)):**
- >= 0 (no negative amounts in base tables)
- <= 9,999,999.99 (max 10 digits before decimal)
- Exception: `credit_notes.amount` can be negative (reversal)

**Invoice total:**
- `invoices.total = SUM(invoice_line_items.amount)` (enforced at insert time, not DB constraint)
- `invoice_line_items.tax_rate` / `tax_amount` are immutable once the invoice is issued.

**Deposit:**
- `deposits.amount <= reservations.pricing_snapshot.deposit_required`
- `deposits.amount_released <= deposits.amount`

---

### Category 6 — Ownership Validations

**Permission check:** Every query includes `WHERE company_id = :company_id` (and `agency_id = :agency_id` for agency-scoped data).

**User scope:** User can only access their company. Cross-company access is forbidden at all layers.

**Agency scope:** User can only access agencies they're members of (checked via `agency_memberships`).

---

### Category 7 — Subscription Validations

**Feature flag check:** Before creating resource, check:
```sql
SELECT 1 FROM plan_features pf
JOIN companies c ON c.plan_id = pf.plan_id
WHERE c.id = :company_id AND pf.feature_key = :feature
```

Example: Before creating a custom role, check `'custom_roles'` is enabled.

**Limit check:** Before creating resource, check:
```sql
SELECT limit_value FROM plan_limits 
WHERE plan_id = :plan_id AND limit_key = :key
-- Compare COUNT(*) against limit
```

Example: Before creating vehicle, ensure `COUNT(*) < max_vehicles` limit.

---

### Category 8 — Status Validations

**Reservation status transitions:**
```
'pending' → 'confirmed' (customer accepts)
'confirmed' → 'active' (vehicle picked up)
'active' → 'completed' (vehicle returned)
'pending' OR 'confirmed' → 'cancelled' (cancel before pickup)
```

**Contract status transitions:**
```
'draft' → 'unsigned' (generated from reservation)
'unsigned' → 'signed' (customer e-signs)
'signed' → 'fulfilled' (completed after vehicle return)
```

**Invoice status transitions:**
```
'draft' → 'issued' (sent to customer)
'issued' → 'paid' (payment recorded)
'issued' → 'overdue' (due date passed without payment)
'issued' OR 'overdue' → 'cancelled' (credit note issued)
```

**Illegal transitions** are rejected at the application layer with a clear error message. Database constraints do not prevent (to avoid complex CHECK logic).

**Required fields (NOT NULL):**

```sql
ALTER TABLE reservations ADD CONSTRAINT ck_reservation_status CHECK (
```

```sql
ALTER TABLE reservations ADD CONSTRAINT ck_reservation_dates CHECK (

);
```

```sql
ALTER TABLE documents ADD CONSTRAINT ck_document_entity_type CHECK (
  entity_type IN ('vehicle', 'customer', 'contract', 'reservation', 'expense', 'agency', 'invoice')
);
```

**Role scope constraint:**

```sql
ALTER TABLE role_permissions ADD CONSTRAINT ck_role_permission_scope CHECK (
  -- This is enforced at the application layer; database can't enforce cross-table checks
);
```

---

### Reference Integrity (Foreign Keys)

**Standard cascade:**

- ON DELETE RESTRICT (prevent deletion if children exist)
- ON DELETE SET NULL (for optional references)
- ON DELETE CASCADE (rare, only for non-critical data)

**Exception: Soft-delete aware deletes**

When a parent is soft-deleted, children are NOT automatically soft-deleted. Application logic soft-deletes children independently. Example: When an agency is soft-deleted, its vehicles are NOT auto-soft-deleted. Vehicles remain with `agency_id` pointing to the deleted agency (which is still queryable via `deleted_at IS NOT NULL`).

---

### Historical Integrity

**Immutable records:**

- `created_at` is never updated (database constraint: READ-ONLY after insert)
- `deleted_at` is set once and never changed
- Append-only tables (`audit_logs`, `activity_logs`, `vehicle_mileage_logs`) never update any field

**Snapshot immutability:**

- `reservation_pricing_snapshots` rows are inserted once and never updated
- A price change creates a new snapshot row with `supersedes_id` reference to the old one
- Queries always select the latest (highest `created_at`) snapshot per reservation
- `reservation_pricing_snapshots.tax_rate` stores the immutable accepted tax rate copied from resolved agency settings at snapshot creation. Existing historical rows may be `NULL` if that rate was not stored.

---

### Immutability for Business Records

**Never update:**
- Invoices (issue a credit note for corrections)
- Contracts (once signed, immutable)
- Audit logs (append-only)
- Payment records (once recorded, immutable)

**Soft-delete only:**
- Company, agencies, users, vehicles, customers, reservations (business data)
- Never hard-delete anything business-related

## 7. Performance Rules

### Pagination Strategy

**Standard:** Offset-limit pagination (simple but slow for large offsets).

```sql
SELECT * FROM reservations 
WHERE company_id = :company_id AND deleted_at IS NULL
ORDER BY created_at DESC
LIMIT 50 OFFSET :offset
```

**For large datasets:** Keyset pagination (resume from last row).

```sql
SELECT * FROM reservations 
WHERE company_id = :company_id 
AND deleted_at IS NULL
AND created_at < :last_created_at  -- Resume from last row
ORDER BY created_at DESC
LIMIT 50
```

---

### Search Strategy

**Exact match:** Indexed column
```sql
SELECT * FROM customers 
WHERE company_id = :company_id AND full_name = :name AND deleted_at IS NULL
```

**Partial match (name search):** GIN trigram index
```sql
CREATE INDEX idx_customer_name_search ON customers USING GIN(full_name gin_trgm_ops);

SELECT * FROM customers 
WHERE company_id = :company_id 
AND full_name ILIKE '%' || :term || '%' 
AND deleted_at IS NULL
LIMIT 50
```

---

### Filtering Strategy

**Single filter:** Use indexed column
```sql
SELECT * FROM reservations 
WHERE company_id = :company_id AND status = 'active' AND deleted_at IS NULL
ORDER BY created_at DESC
LIMIT 50
```

**Multiple filters:** Composite index on common combinations
```
CREATE INDEX idx_reservation_filters ON reservations(
  company_id, 
  agency_id, 
  status, 
  deleted_at
)
```

---

### Sorting Strategy

**Default:** Sort by `created_at DESC` (newest first).

**Alternative sorts:**
- By `name` (alphabetical)
- By `total` (financial)
- By `status` (grouping)

**All sorts use indexed columns.** No sorting on unindexed columns without a small LIMIT (application handles).

---

### Aggregations (Dashboard KPIs)

**Count active:**
```sql
SELECT COUNT(*) FROM reservations 
WHERE company_id = :company_id AND status = 'active' AND deleted_at IS NULL
```

**Sum revenue (month-to-date):**
```sql
SELECT SUM(total) FROM invoices 
WHERE company_id = :company_id 
AND created_at >= date_trunc('month', now())
AND deleted_at IS NULL
```

**Count by status:**
```sql
SELECT status, COUNT(*) FROM reservations 
WHERE company_id = :company_id AND deleted_at IS NULL
GROUP BY status
```

**All aggregations use indexed columns.** For large companies, cache results in Redis (Phase 2).

---

### Caching Strategy

**What to cache:**
- Plan limits and features (rarely change, queried on every operation)
- Roles and permissions (seeded, rarely change)
- Vehicle categories (company-scoped, rarely change)
- Settings (could be queried frequently)

**What NOT to cache:**
- Reservations (mutable, too frequent to cache invalidate)
- Invoices (mutable)
- Customer data (mutable)
- Audit/activity logs (append-only, always fresh query)

**Cache invalidation:** On write, invalidate the cache key immediately.

---

### Reporting and Archive Strategy

**Hot data:** Recent 90 days in main tables.

**Warm data:** 90-180 days, queried via materialized views (Phase 2).

**Cold data:** 180+ days, archived to separate schema or hard-deleted after compliance hold.

**Partition strategy (future):**
```sql
CREATE TABLE audit_logs_2024_01 PARTITION OF audit_logs 
FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
```

Monthly partitions allow efficient deletion of old data (drop partition instead of DELETE).

## 8. Security Rules

### Tenant Isolation

**Rule:** Every query includes `WHERE company_id = :company_id`.

**Implementation:** Middleware validates `user.company_id` matches the requested resource's `company_id`.

**Breach scenario:** Query returns data from wrong tenant if `company_id` check is forgotten. Prevents this with automated checks (tests verify isolation).

---

### Agency Isolation

**Rule:** Users see only data from agencies they're members of.

**Implementation:** Query checks `user_id IN (SELECT user_id FROM agency_memberships WHERE agency_id = :agency_id)`.

**Exception:** Company-level users (owner, billing manager) see all agencies.

---

### Permission Boundaries

**Rule:** Permission check is 4-step (see System Blueprint).

1. Load `user.company_id` (company membership required)
2. Load agency membership for this agency (required for agency-scoped operations)
3. Load role from membership (`role_id`)
4. Query `role_permissions` for the required permission key

**If any step fails:** Reject operation immediately. Never fall back to default permissions.

---

### Sensitive Fields

**Never returned to client:**
- `password_hash` (doesn't exist; Better Auth manages this separately)
- `token_hash` (invitations only; plain token sent via email)

**Encrypted at rest (Phase 2):**
- SSN / ID numbers
- Passport numbers
- Credit card details (never stored; Stripe handles)

**Redacted in audit logs:**
- Document content (store document ID instead)
- Exact amounts over some threshold (for insider trading concerns)

---

### Hidden Fields (Application Layer)

**Invisible to regular users:**
- `deleted_at`, `deleted_by` (admin only)
- `created_by`, `updated_by` (admin only)
- Full audit trail (admin only)

---

### Owner-Only Fields

**Cannot be changed by non-owner:**
- `company.plan_id` (affects limits)
- `company.status` (suspension)
- `users.role_id` (permission elevation)

---

### Admin-Only Tables

**No customer access:**
- `audit_logs` (read-only by admin via Activity Log UI)
- `role_permissions`
- `user_permission_overrides`
- `plan_limits`, `plan_features`

---

### Read-Only Tables

**Platform tables (never modified by users):**
- `permissions`
- `plans`
- `plan_limits`
- `plan_features`

---

### GDPR Strategy (Phase 2)

**Data export:** Dump all data for a user in JSON (anonymized before export).

**Data deletion:** On user request, soft-delete user and all user-created records, then hard-delete after 30-day retention.

## 9. Migration Strategy

### When to Write a Migration

**Schema migration needed when:**
- Adding a new table
- Adding a required column to an existing table
- Removing a column
- Changing column type
- Adding a new index (can be done zero-downtime)
- Adding a new FK constraint

**Migration NOT needed:**
- Adding an optional column with a default
- Adding a new enum value (backward compatible)
- Soft-deleting a table (just stop using it)
- Adding a new row to a reference table (`plans`, `permissions`)

---

### Backward Compatibility

**Rule:** New code must be compatible with the old schema for the duration of the migration.

**Example:** Adding a required column `phone` to `customers`:

1. **Deployment 1:** Add column as optional (`phone TEXT`), add code to handle null
2. **Wait 24 hours:** For all requests to be processed
3. **Deployment 2:** Backfill missing values, add NOT NULL constraint, require phone in forms

**Alternative:** Feature flag the new field (code can't see it until flag is enabled, safe to add/remove).

---

### Adding Tables

**Safe approach:**
1. Create new table
2. Start writing to it (alongside old table for dual-write)
3. Migrate old data
4. Switch reads to new table
5. Remove dual-write
6. Delete old table

---

### Removing Columns

**Deprecated approach:**
1. Stop writing to the column (code ignores it)
2. Wait 30 days
3. Remove the column in a migration

---

### Deprecation Policy

**If a column needs to be removed:**
- Mark as deprecated in code comments
- Announce 6 months before removal
- Provide migration path to new structure
- Remove only after no code references it

---

### Feature Flags for Database Changes

**Example:** Rolling out a new `customer.phone` field safely.

```sql
INSERT INTO plan_features (plan_id, feature_key) VALUES (..., 'customer_phone_field');
-- Gated in code:
if (featureEnabled('customer_phone_field')) {
  // Show phone field in UI, require it in forms
}
```

---

### Zero-Downtime Migrations

**Safe operations:**
- Adding a column with a default value (or NULL)
- Adding an index (non-blocking)
- Adding a CHECK constraint
- Removing an unused column

**Risky operations (require downtime or split):**
- Changing a column type
- Making a nullable column NOT NULL
- Renaming a column
- Removing a required column

---

### Seed Migrations

**Platform seed data (run once at deploy):**

```sql
INSERT INTO plans (id, name, is_active) 
VALUES 
  (uuid1, 'starter', true),
  (uuid2, 'pro', true),
  (uuid3, 'enterprise', true)
ON CONFLICT (name) DO NOTHING;

INSERT INTO permissions (key, domain, description)
VALUES 
  ('reservations.create', 'reservations', 'Create new reservation'),
  ('reservations.view', 'reservations', 'View agency reservations'),
  ...
ON CONFLICT (key) DO NOTHING;
```

**Company seed data (run on registration):**

```sql
-- Create company, default agency, owner user, system roles (see Transaction 1)
```

---

### Reference Data Migrations

**Backfill:** Updating existing rows to populate a new field.

```sql
UPDATE invoices SET currency = 'EUR'
WHERE company_id IN (
  SELECT id FROM companies WHERE country_code = 'FR'
);
```
